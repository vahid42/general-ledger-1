# تحلیل دامنه — سرفصل حسابداری (Account Heading)

**نوع سند:** تحلیل نیازمندی و قواعد کسب‌وکار
**وضعیت:** Draft
**منبع:** تیم تحلیل
**دامنه:** General Ledger
**موضوع:** ساختار و قواعد سرفصل‌های حسابداری

---

## 1. هدف

این سند قواعد کسب‌وکار مربوط به **سرفصل حسابداری (Account Heading)** را مشخص می‌کند.

سرفصل حسابداری برای ایجاد ساختار سلسله‌مراتبی حساب‌ها استفاده می‌شود و شامل چند سطح مشخص از طبقه‌بندی حسابداری است.

در این مدل، سرفصل‌ها به‌صورت یک درخت نگهداری می‌شوند و در پایین‌ترین سطح، امکان تعریف حساب‌های عملیاتی وجود دارد.

---

## 2. ساختار سلسله‌مراتبی

سرفصل‌ها دارای ساختار درختی هستند.

هر سرفصل می‌تواند:

* بدون فرزند باشد.
* دارای یک یا چند فرزند باشد.
* تعداد فرزندان هر سرفصل محدود به مقدار مشخصی نیست.

بنابراین رابطه‌ی والد و فرزند به‌صورت زیر است:

```text
Parent
 ├── Child
 ├── Child
 ├── Child
 └── ...
```

هر سرفصل، به‌جز Root، دقیقاً یک والد دارد.

---

## 3. سطوح سرفصل

ساختار سرفصل دارای **۵ سطح اصلی** به‌علاوه Root است.

سطح‌ها از `0` تا `5` شماره‌گذاری می‌شوند:

| Level | مفهوم     | وضعیت   |
| ----: | --------- | ------- |
|     0 | Root      | ریشه    |
|     1 | سطح اول   | غیر برگ |
|     2 | سطح دوم   | غیر برگ |
|     3 | سطح سوم   | غیر برگ |
|     4 | سطح چهارم | غیر برگ |
|     5 | سطح پنجم  | برگ     |

سطح `5` پایین‌ترین سطح سرفصل است و به‌عنوان **Leaf** شناخته می‌شود.

```text
Level 0 → Root
Level 1
Level 2
Level 3
Level 4
Level 5 → Leaf
```

---

## 4. Root

ساختار سرفصل دارای یک Root است.

Root:

* والد ندارد.
* در Level `0` قرار دارد.
* نقطه شروع درخت سرفصل‌ها است.
* مستقیماً یا غیرمستقیم تمام سرفصل‌ها زیرمجموعه‌ی آن هستند.
* سرفصل عملیاتی محسوب نمی‌شود.
* دارای `Nature` و `allowNegativeBalance` عملیاتی نیست.

نمونه:

| id | parent | code      | name | level |
| -: | -----: | --------- | ---- | ----: |
|  1 |   null | 100000000 | روت  |     0 |

---

## 5. نمونه ساختار سرفصل

نمونه‌ی زیر یک ساختار معتبر از سرفصل‌ها را نشان می‌دهد:

```text
Root
│
├── بهکار
│   │
│   └── بهکار / اول
│       │
│       └── بهکار / اول / دوم
│           │
│           └── بهکار چهارم
│               ├── بهکار پنجم
│               └── بهکار ششم
│
└── بستانکار
```

نمونه اطلاعات:

| id | parent | code      | name          | nature | allowNegativeBalance | leaf | level |
| -: | -----: | --------- | ------------- | ------ | -------------------: | ---: | ----: |
|  1 |   null | 100000000 | روت           | null   |                 null |    0 |     0 |
|  2 |      1 | 101000000 | بهکار         | DEBIT  |                    0 |    0 |     1 |
|  3 |      1 | 102000000 | بستانکار      | CREDIT |                    1 |    0 |     1 |
|  4 |      2 | 101010000 | بهکار/اول     | DEBIT  |                    0 |    0 |     2 |
|  5 |      4 | 101010000 | بهکار/اول/دوم | DEBIT  |                    0 |    0 |     3 |
|  6 |      5 | 101010100 | بهکار چهارم   | DEBIT  |                    0 |    0 |     4 |
|  7 |      6 | 101010101 | بهکار پنجم    | DEBIT  |                    0 |    1 |     5 |
|  8 |      6 | 101010102 | بهکار ششم     | DEBIT  |                    0 |    1 |     5 |

> **نکته تحلیل:** در نمونه فوق، کد `101010000` برای رکوردهای 4 و 5 تکرار شده است که با قاعده Unique بودن Code مغایرت دارد. این مورد باید در داده‌های نمونه اصلاح شود.

---

## 6. ویژگی‌های سرفصل

هر سرفصل شامل ویژگی‌های زیر است:

| ویژگی                | توضیح                  |
| -------------------- | ---------------------- |
| id                   | شناسه سرفصل            |
| parent               | سرفصل والد             |
| code                 | کد یکتای سرفصل         |
| name                 | نام سرفصل              |
| nature               | ماهیت حساب             |
| allowNegativeBalance | امکان داشتن مانده منفی |
| leaf                 | مشخص‌کننده برگ بودن    |
| level                | سطح سرفصل              |

---

## 7. یکتایی Code

کد سرفصل باید در کل ساختار سرفصل‌ها **یکتا** باشد.

دو سرفصل نمی‌توانند Code یکسان داشته باشند.

این قانون مستقل از Parent است.

یعنی حتی اگر دو سرفصل والد متفاوت داشته باشند، باز هم نمی‌توانند Code یکسان داشته باشند.

### مثال نامعتبر

```text
Parent A
 └── Code: 101010101

Parent B
 └── Code: 101010101
```

این ساختار مجاز نیست.

---

## 8. عدم تغییر Code

پس از ایجاد سرفصل، `Code` آن قابل تغییر نیست.

مثلاً اگر سرفصل با کد:

```text
101010101
```

ایجاد شده باشد، تغییر آن به:

```text
101010102
```

مجاز نیست.

---

## 9. عدم جابه‌جایی سرفصل

یک سرفصل پس از ایجاد نمی‌تواند به والد دیگری منتقل شود.

مثلاً اگر:

```text
A
└── B
    └── C
```

باشد، انتقال `C` به:

```text
A
└── C
```

یا:

```text
X
└── C
```

مجاز نیست.

بنابراین ساختار والد-فرزند سرفصل‌ها پس از ایجاد ثابت است.

---

## 10. محدودیت تعداد سطوح

بیشترین سطح مجاز برای سرفصل، Level `5` است.

بنابراین ایجاد سرفصل زیر یک سرفصل Level `5` مجاز نیست.

### نامعتبر

```text
Level 5
└── Level 6 ❌
```

### معتبر

```text
Level 4
└── Level 5 ✅
```

شرط ایجاد فرزند:

```text
parent.level < 5
```

و Level فرزند همیشه برابر است با:

```text
parent.level + 1
```

---

## 11. Leaf

سرفصل Level `5` به‌عنوان Leaf شناخته می‌شود.

قاعده:

```text
level == 5 → leaf == true
level < 5  → leaf == false
```

Leaf نمی‌تواند دارای سرفصل فرزند باشد.

---

## 12. رابطه سرفصل و حساب

تعریف حساب عملیاتی در پایین‌ترین سطح سرفصل انجام می‌شود.

حساب‌ها مستقیماً زیر یک سرفصل Leaf قرار می‌گیرند.

ساختار کلی:

```text
Root
  └── Heading
       └── Heading
            └── Heading
                 └── Heading
                      └── Leaf
                           ├── Account 1
                           ├── Account 2
                           ├── Account 3
                           └── ...
```

هر سرفصل Leaf می‌تواند دارای:

```text
1 .. N
```

حساب باشد.

تعداد حساب‌های زیر یک سرفصل Leaf محدود نشده است.

---

## 13. حساب زیر سرفصل غیر Leaf

حساب عملیاتی نباید مستقیماً زیر سرفصل‌های غیر Leaf تعریف شود.

بنابراین:

```text
Level 1 → Account ❌
Level 2 → Account ❌
Level 3 → Account ❌
Level 4 → Account ❌
Level 5 → Account ✅
```

---

## 14. حذف سرفصل

حذف سرفصل فقط در صورتی مجاز است که شرایط زیر برقرار باشد:

1. سرفصل در پایین‌ترین سطح یعنی Level `5` باشد.
2. سرفصل دارای هیچ Child نباشد.
3. هیچ Accountای به آن سرفصل متصل نباشد.

بنابراین:

```text
Level < 5
    ↓
Delete ❌
```

و:

```text
Level 5
    │
    ├── Has Child
    │      ↓
    │    Delete ❌
    │
    └── No Child
           │
           ├── Has Account
           │      ↓
           │    Delete ❌
           │
           └── No Account
                  ↓
                Delete ✅
```

### مثال

اگر ساختار به شکل زیر باشد:

```text
A
└── B
```

حذف `A` مجاز نیست.

اگر:

```text
A (Level 5)
```

باشد ولی دارای Account باشد:

```text
A
├── Account 1
└── Account 2
```

حذف `A` نیز مجاز نیست.

فقط در شرایط زیر حذف مجاز است:

```text
A (Level 5)
```

بدون Child و بدون Account.

---

## 15. وراثت Nature

ماهیت (`Nature`) سرفصل از والد به فرزند منتقل می‌شود.

اگر یک سرفصل دارای ماهیت مشخصی باشد، سرفصل فرزند باید همان ماهیت را داشته باشد.

مثال:

```text
Parent
Nature = DEBIT

└── Child
    Nature = DEBIT
```

بنابراین:

```text
Parent:
Nature = DEBIT

Child:
Nature = CREDIT ❌
```

مجاز نیست.

---

## 16. وراثت Allow Negative Balance

ویژگی `allowNegativeBalance` نیز از والد به فرزند منتقل می‌شود.

فرزند نمی‌تواند این ویژگی را مستقل از والد تعیین کند.

مثال:

```text
Parent:
allowNegativeBalance = false

Child:
allowNegativeBalance = true ❌
```

مقدار صحیح:

```text
Parent:
allowNegativeBalance = false

Child:
allowNegativeBalance = false ✅
```

---

## 17. Root و ویژگی‌های Nature

Root صرفاً ریشه‌ی ساختار است و سرفصل عملیاتی محسوب نمی‌شود.

بنابراین:

```text
Root
nature = null
allowNegativeBalance = null
```

ویژگی‌های عملیاتی `Nature` و `allowNegativeBalance` از اولین سطح واقعی سرفصل مشخص می‌شوند.

---

## 18. قواعد تغییر ساختار

پس از ایجاد سرفصل، موارد زیر مجاز نیستند:

| عملیات                                     | مجاز |
| ------------------------------------------ | ---- |
| تغییر Code                                 | ❌    |
| تغییر Parent                               | ❌    |
| انتقال سرفصل به شاخه دیگر                  | ❌    |
| ایجاد Child برای Level 5                   | ❌    |
| ایجاد Level بیشتر از 5                     | ❌    |
| تغییر Nature مستقل از Parent               | ❌    |
| تغییر AllowNegativeBalance مستقل از Parent | ❌    |

تغییر `name` در صورت تأیید کسب‌وکار مجاز است.

---

## 19. قواعد ایجاد سرفصل

برای ایجاد یک سرفصل جدید:

1. Parent باید معتبر باشد، مگر اینکه سرفصل Root باشد.
2. Level فرزند باید دقیقاً یک واحد بیشتر از Level والد باشد.
3. Level نباید بیشتر از `5` باشد.
4. Code باید Unique باشد.
5. اگر Parent دارای Nature باشد، Nature فرزند باید از Parent به ارث برسد.
6. مقدار `allowNegativeBalance` باید از Parent به ارث برسد.
7. اگر Level برابر `5` باشد، سرفصل Leaf است.
8. اگر Level کمتر از `5` باشد، سرفصل Leaf نیست.

---

## 20. قواعد ایجاد فرزند

اگر سرفصل فعلی در Level `N` باشد، فرزند آن باید در:

```text
N + 1
```

قرار بگیرد.

مثال:

```text
Level 1
   ↓
Level 2

Level 2
   ↓
Level 3

Level 3
   ↓
Level 4

Level 4
   ↓
Level 5
```

اما:

```text
Level 5
   ↓
Level 6 ❌
```

مجاز نیست.

---

## 21. ویژگی‌های Immutable ساختاری

بر اساس قواعد فعلی، ویژگی‌های زیر بعد از ایجاد ثابت هستند:

* `code`
* `parent`
* `level`

این ویژگی‌ها بخشی از ساختار سلسله‌مراتبی سرفصل هستند و تغییر آنها مجاز نیست.

---

## 22. خلاصه قواعد کسب‌وکار

### ساختار

* سرفصل‌ها ساختار Tree دارند.
* یک Root وجود دارد.
* Root در Level `0` است.
* هر Parent می‌تواند `1..N` Child داشته باشد.
* حداکثر Level برابر `5` است.
* Level `5` تنها سطح Leaf است.

### Code

* Code باید Unique باشد.
* Code بعد از ایجاد قابل تغییر نیست.

### Parent

* هر سرفصل غیر Root دقیقاً یک Parent دارد.
* Parent بعد از ایجاد قابل تغییر نیست.
* سرفصل قابل انتقال به Parent دیگر نیست.

### Nature

* Nature از Parent به Child به ارث می‌رسد.
* Child نمی‌تواند Nature متفاوتی نسبت به Parent داشته باشد.

### Allow Negative Balance

* `allowNegativeBalance` از Parent به Child به ارث می‌رسد.
* Child نمی‌تواند مقدار متفاوتی نسبت به Parent داشته باشد.

### Leaf

* Level `5` باید Leaf باشد.
* Leaf نمی‌تواند Child داشته باشد.
* زیر Levelهای کمتر از `5` حساب عملیاتی تعریف نمی‌شود.

### Account

* حساب‌ها فقط زیر سرفصل‌های Leaf تعریف می‌شوند.
* هر Leaf می‌تواند `1..N` حساب داشته باشد.
* Leaf دارای Account قابل حذف نیست.

### Delete

* سرفصل غیر Leaf قابل حذف نیست.
* سرفصل دارای Child قابل حذف نیست.
* سرفصل دارای Account قابل حذف نیست.
* سرفصل Level `5` بدون Child و بدون Account قابل حذف است.

---

## 23. نکات نیازمند تصمیم تیم تحلیل

موارد زیر همچنان نیازمند تعیین تکلیف هستند:

1. آیا Root فقط یک رکورد در کل سیستم دارد؟
2. آیا `code` توسط کاربر تعیین می‌شود یا توسط سیستم تولید می‌شود؟
3. قاعده دقیق تولید Code چیست؟
4. آیا تغییر `name` بعد از ایجاد مجاز است؟
5. آیا حذف فیزیکی است یا Soft Delete؟
6. آیا تغییر `name` باید تاریخچه داشته باشد؟
7. آیا `nature` و `allowNegativeBalance` بعد از ایجاد برای تمام سرفصل‌ها Immutable هستند؟
8. آیا حساب فقط و فقط زیر Level `5` قابل ایجاد است؟
9. آیا Leaf می‌تواند بدون Account باقی بماند؟
10. آیا ایجاد اولین سرفصل نیازمند وجود Root است؟
11. آیا هر ساختار سرفصل فقط یک Root دارد یا ممکن است چند Root مستقل وجود داشته باشد؟
12. آیا Code باید با Level و Parent رابطه‌ی ساختاری مشخصی داشته باشد؟

---

## 24. نتیجه تحلیل فعلی

مدل سرفصل یک **درخت ساختاری ثابت با حداکثر پنج سطح عملیاتی** است که در پایین‌ترین سطح به حساب‌های عملیاتی متصل می‌شود.

```text
Root
 │
 ├── Heading
 │    │
 │    └── Heading
 │         │
 │         └── Heading
 │              │
 │              └── Heading
 │                   │
 │                   └── Leaf
 │                        ├── Account
 │                        ├── Account
 │                        └── Account
 │
 └── Heading
      └── ...
```

در این مدل:

* ساختار سرفصل پس از ایجاد پایدار است.
* Code و Parent قابل تغییر نیستند.
* سرفصل‌ها قابل جابه‌جایی نیستند.
* Level حداکثر `5` است.
* Level `5` تنها سطح Leaf است.
* Nature و AllowNegativeBalance در طول شاخه از Parent به Child منتقل می‌شوند.
* Account فقط زیر Leaf قرار می‌گیرد.
* Leaf دارای Account قابل حذف نیست.
* سرفصل فقط در صورت قرار داشتن در Level `5`، نداشتن Child و نداشتن Account قابل حذف است.

این سند **تحلیل دامنه و قواعد کسب‌وکار** است و جزئیات پیاده‌سازی فنی مانند Aggregate، Entity، Value Object، Repository و Domain Service در آن تعریف نمی‌شود.
