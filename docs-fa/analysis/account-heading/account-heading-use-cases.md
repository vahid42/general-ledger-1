# 4. UC-01 — Create Account Heading

## عنوان

**ایجاد سرفصل حسابداری**

## Actor

`User`

## هدف

ایجاد یک سرفصل جدید در ساختار سلسله‌مراتبی سرفصل‌های حسابداری.

## پیش‌شرط‌ها

* کاربر مجوز ایجاد سرفصل را داشته باشد.
* در صورت وجود Parent، Parent معتبر باشد.
* ساختار فعلی امکان ایجاد سرفصل جدید را داشته باشد.

## ورودی‌ها

| ورودی                  | توضیح                          |
| ---------------------- | ------------------------------ |
| `parentId`             | شناسه سرفصل والد               |
| `code`                 | کد سرفصل                       |
| `name`                 | نام سرفصل                      |
| `nature`               | ماهیت، در صورت نیاز            |
| `allowNegativeBalance` | امکان مانده منفی، در صورت نیاز |

> تعیین نهایی `nature` و `allowNegativeBalance` تابع قواعد دامنه است. برای Child این مقادیر از Parent به ارث می‌رسند.

## جریان اصلی

1. کاربر درخواست ایجاد سرفصل را ارسال می‌کند.
2. سیستم درخواست را دریافت می‌کند.
3. در صورت وجود `parentId`، سیستم Parent را پیدا می‌کند.
4. سیستم امکان ایجاد سرفصل زیر Parent را بررسی می‌کند.
5. سیستم یکتا بودن Code را بررسی می‌کند.
6. سیستم سرفصل جدید را ایجاد می‌کند.
7. سیستم نتیجه ایجاد را ذخیره می‌کند.
8. سیستم نتیجه ایجاد را برمی‌گرداند.

## حالت ایجاد Root

اگر `parentId` وجود نداشته باشد، سیستم درخواست را به‌عنوان ایجاد Root در نظر می‌گیرد.

```text
parentId = null
    ↓
Create Root
```

## حالت ایجاد Child

اگر `parentId` وجود داشته باشد:

```text
parentId != null
    ↓
Find Parent
    ↓
Create Child
```

## جریان‌های جایگزین

### A1 — Parent وجود ندارد

اگر Parent مشخص‌شده پیدا نشود:

```text
Create ❌
```

سیستم درخواست را رد می‌کند.

### A2 — Parent در Level 5 است

اگر Parent در Level `5` باشد:

```text
Create Child ❌
```

سیستم درخواست را رد می‌کند.

### A3 — Code تکراری است

اگر Code قبلاً استفاده شده باشد:

```text
Create ❌
```

سیستم درخواست را رد می‌کند.

### A4 — اطلاعات ورودی نامعتبر است

اگر اطلاعات موردنیاز معتبر نباشند، سیستم درخواست را رد می‌کند.

## پس‌شرط

در صورت موفقیت، یک Account Heading جدید در ساختار سرفصل ایجاد شده است.

# 5. UC-02 — Update Account Heading

## عنوان

**ویرایش سرفصل حسابداری**

## Actor

`User`

## هدف

تغییر اطلاعات قابل ویرایش یک سرفصل موجود.

## پیش‌شرط‌ها

* سرفصل موردنظر وجود داشته باشد.
* کاربر مجوز ویرایش داشته باشد.

## ورودی‌ها

| ورودی       | توضیح       |
| ----------- | ----------- |
| `headingId` | شناسه سرفصل |
| `name`      | نام جدید    |

در نسخه فعلی، تنها `name` به‌عنوان ویژگی قابل تغییر در نظر گرفته می‌شود.

## جریان اصلی

1. کاربر سرفصل موردنظر را انتخاب می‌کند.
2. سیستم سرفصل را پیدا می‌کند.
3. سیستم اطلاعات قابل ویرایش را دریافت می‌کند.
4. سیستم تغییر مجاز را اعمال می‌کند.
5. سیستم سرفصل را ذخیره می‌کند.
6. سیستم نتیجه ویرایش را برمی‌گرداند.

## محدودیت‌ها

ویژگی‌های زیر قابل تغییر نیستند:

```text
code       ❌
parent     ❌
level      ❌
```

همچنین تغییر مستقل موارد زیر مجاز نیست:

```text
nature
allowNegativeBalance
```

## جریان‌های جایگزین

### A1 — سرفصل وجود ندارد

```text
Update ❌
```

سیستم درخواست را رد می‌کند.

### A2 — تلاش برای تغییر Code

```text
Update ❌
```

سیستم تغییر Code را رد می‌کند.

### A3 — تلاش برای تغییر Parent

```text
Update ❌
```

سیستم تغییر Parent را رد می‌کند.

### A4 — تلاش برای تغییر Level

```text
Update ❌
```

سیستم تغییر Level را رد می‌کند.

## پس‌شرط

در صورت موفقیت، نام سرفصل به‌روزرسانی شده است.

# 6. UC-03 — Delete Account Heading

## عنوان

**حذف سرفصل حسابداری**

## Actor

`User`

## هدف

حذف یک سرفصل از ساختار سرفصل‌ها.

## پیش‌شرط‌ها

* سرفصل موردنظر وجود داشته باشد.
* کاربر مجوز حذف داشته باشد.

## ورودی‌ها

| ورودی       | توضیح       |
| ----------- | ----------- |
| `headingId` | شناسه سرفصل |

## جریان اصلی

1. کاربر درخواست حذف سرفصل را ارسال می‌کند.
2. سیستم سرفصل را پیدا می‌کند.
3. سیستم شرایط حذف را بررسی می‌کند.
4. سیستم وجود Child را بررسی می‌کند.
5. سیستم وجود Account را بررسی می‌کند.
6. در صورت مجاز بودن، سرفصل حذف می‌شود.
7. سیستم نتیجه عملیات را برمی‌گرداند.

## شرایط حذف

حذف فقط زمانی مجاز است که:

```text
Level == 5
AND
No Child
AND
No Account
```

## جریان‌های جایگزین

### A1 — سرفصل وجود ندارد

```text
Delete ❌
```

سیستم درخواست را رد می‌کند.

### A2 — سرفصل Leaf نیست

اگر Level کمتر از `5` باشد:

```text
Delete ❌
```

### A3 — سرفصل دارای Child است

اگر سرفصل دارای فرزند باشد:

```text
Delete ❌
```

### A4 — سرفصل دارای Account است

اگر حسابی به سرفصل متصل باشد:

```text
Delete ❌
```

## پس‌شرط

در صورت موفقیت، سرفصل از ساختار سیستم حذف شده است.

# 7. UC-04 — Search Account Headings

## عنوان

**جستجوی سرفصل‌های حسابداری**

## Actor

`User`

## هدف

پیدا کردن و مشاهده سرفصل‌های حسابداری بر اساس معیارهای جستجو.

## پیش‌شرط‌ها

* کاربر مجوز مشاهده سرفصل‌ها را داشته باشد.

## ورودی‌ها

| معیار      | توضیح           |
| ---------- | --------------- |
| `id`       | شناسه سرفصل     |
| `code`     | کد سرفصل        |
| `name`     | نام سرفصل       |
| `parentId` | شناسه والد      |
| `level`    | سطح سرفصل       |
| `leaf`     | وضعیت Leaf بودن |
| `nature`   | ماهیت           |

> مجموعه نهایی فیلترها باید توسط تحلیل کسب‌وکار تأیید شود.

## جریان اصلی

1. کاربر معیارهای جستجو را وارد می‌کند.
2. سیستم درخواست جستجو را دریافت می‌کند.
3. سیستم سرفصل‌های منطبق را پیدا می‌کند.
4. سیستم نتایج را برمی‌گرداند.

## جریان‌های جایگزین

### A1 — هیچ نتیجه‌ای وجود ندارد

```text
Result = Empty
```

سیستم نتیجه خالی برمی‌گرداند.

### A2 — معیار جستجوی نامعتبر

اگر معیار جستجو نامعتبر باشد:

```text
Search ❌
```

سیستم درخواست را رد می‌کند.

## پس‌شرط

هیچ تغییری در ساختار سرفصل ایجاد نمی‌شود.

# 9. مرز مسئولیت Use Case و Domain

Use Case مسئول **Orchestration** عملیات سیستم است.

به‌صورت مفهومی:

```text
Use Case
   │
   ├── دریافت Request
   ├── پیدا کردن Aggregate
   ├── هماهنگی عملیات
   ├── فراخوانی رفتار Domain
   └── ذخیره نتیجه
```

قواعد اصلی کسب‌وکار در Domain قرار دارند.

برای مثال:

```text
Code باید Unique باشد
```

یا:

```text
Level 5 نمی‌تواند Child داشته باشد
```

یا:

```text
Leaf دارای Account قابل حذف نیست
```

این قواعد در:

```text
account-heading-analysis.md
```

تعریف شده‌اند.

# 12. تصمیمات باز

موارد زیر هنوز نیازمند تصمیم تیم تحلیل هستند:

1. آیا ایجاد Root یک Use Case مستقل است؟
2. آیا Root توسط سیستم به‌صورت خودکار ایجاد می‌شود؟
3. آیا Code توسط کاربر وارد می‌شود یا سیستم آن را تولید می‌کند؟
4. آیا Update فقط شامل تغییر `name` است؟
5. آیا Delete به‌صورت Hard Delete انجام می‌شود یا Soft Delete؟
6. آیا Search باید امکان نمایش ساختار Tree را داشته باشد؟
7. آیا Search باید Pagination داشته باشد؟
8. آیا Search بر اساس Code دقیق است یا Partial Search نیز مجاز است؟
9. آیا Permissionهای Create / Update / Delete / Search از یکدیگر جدا هستند؟
10. آیا Create / Update / Delete باید Audit شوند؟
